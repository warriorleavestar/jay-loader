# Amber Fabric API bridge on NeoForge 21.1.x: design brief

(Design brief, 2026-11-05. It is reference material: what we observe on the real jars wins over it. Items marked (unverified) must be checked with javap first.)

What was read: FabricMC/fabric branch 1.21.1 at 83c07162d88a; neoforged/NeoForge branch 1.21.1 at 624c929f4992 (head dated 2026-10-24, about a year newer than 21.1.265; no 21.1.x tags; CHECK EVERY TARGET AGAINST THE BAKED 21.1.265 JAR); Sinytra/ForgifiedFabricAPI (FFAPI) 1.21.1 at 204211bf9c26 (prior art, Apache-2.0, ideas only). (unverified) marks items not re-checked against source. Strategies: RUN (as-is), FIX (retarget or remap), REBASE (keep the API, implement on NeoForge), DROP.

## 1. Architecture
1. Packaging a re-based module. Keep the official 0.116.17 jar's net.fabricmc.fabric.api.* classes byte-identical. Replace impl.* classes at the same FQNs, keep the module's mod id and version so dependents resolve. Apply the module's access widener (networking ships fabric-networking-api-v1.accesswidener). At bake time veto the listed mixins per class, or strip single injectors where the fixer supports it.
2. One producer per Fabric callback. Each callback gets either the Fabric mixin or a NeoForge-event bridge, never both. Pairs verified to fire twice if both run: DataPackContentsMixin + TagsUpdatedEvent; CommandManagerMixin + RegisterCommandsEvent; item RegistriesMixin + ModifyDefaultComponentsEvent; ItemGroupMixin + BuildCreativeModeTabContentsEvent; InGameHudMixin TAIL + RenderGuiEvent.Post; GameOptionsMixin + RegisterKeyMappingsEvent. (FFAPI LifecycleEventsImpl)
3. NeoForge lifecycle. CommonModLoader.begin: (1) gatherAndInitializeMods (FML constructors); (2) init task "Registry initialization": postNewRegistryEvent (NewRegistryEvent, then DataPackRegistryEvent.NewRegistry, then ModifyRegistriesEvent, then pendingModdedRegistries=null), GameData.unfreezeData, postRegisterEvents, freezeData. load posts FMLCommonSetupEvent, sided setup, then RegistrationEvents.init (ModifyDefaultComponentsEvent, initDataMaps). finish runs IMC, FMLLoadCompleteEvent, then init task "Network registry lock" = NetworkRegistry.setup, which posts RegisterPayloadHandlersEvent inside it. On the server, ServerModLoader.load() is called right after Util.startTimerHackThread().
4. Client order inside Minecraft.<init>: options exist; new ReloadableResourceManager; ClientModLoader.begin; BlockColors/ItemColors.createDefault post RegisterColorHandlersEvent.Block/.Item; new ParticleEngine then RegisterParticleProvidersEvent; new LevelRenderer then RenderLevelStageEvent.RegisterStageEvent; initClientHooks posts RegisterMenuScreensEvent, RegisterClientReloadListenersEvent, RegisterLayerDefinitions, RegisterRenderers, tooltip factories, RegisterKeyMappingsEvent, RegisterGuiLayersEvent, dimension effects, named render types, ColorResolvers, more; first resource reload posts FMLClientSetupEvent; finishModLoading sets isLoading=false and runs options.load(true).
5. Fabric entrypoint window. Run main, then client/server, at HEAD of GameData.postRegisterEvents (inject there or patch Amber's CommonModLoader lambda). That is after unfreezeData and before getRegistrationOrder() is captured, and before the color events, RegisterKeyMappingsEvent and the payload lock. Do NOT run them from a RegisterEvent handler: the order set is captured before the first event, and HIGHEST priority only orders listeners within one mod container. An exception thrown from this window skips revertToVanilla; report it with the Fabric mod id.
6. Load Fabric mod classes lazily. Any static Registry.register before the window hits a frozen registry. Entries made before ModifyRegistriesEvent also miss NeoForge's AddCallbacks (Item.BY_BLOCK, the POI map). (NeoForgeRegistriesSetup)
7. The FabricLoader shim must: project NeoForge [modproperties] into ModMetadata custom values (at least fabric-renderer-api-v1:contains_renderer and fabric-renderer-indigo:force_compatibility); enumerate FML mod roots (client tags need this); expose a minecraft container whose findPath resolves /assets/minecraft/lang/en_us.json; never put Fabric mods into FML ModList as IModFiles; dedupe jar-in-jar ids.
8. Fixer categories: (a) missing target; (b) DEAD TARGET: a deprecated wrapper delegates to a NeoForge overload. Known: ModelBlockRenderer.tesselateBlock 10->12 args, HumanoidArmorLayer.renderArmorPiece 6->12, BlockRenderDispatcher.renderBatched 7->9, SectionCompiler.compile 4->5, ServerPlayer.openMenu 1->2. MOVE the injector to the overload, do not copy it. (c) WRONG TIME: hook fires where it does nothing useful (Options.load()V, BuiltInRegistries.freeze). (d) Lambdas: in classes NeoForge does not patch (ReloadableServerRegistries, EntityRenderers) only the intermediary->Mojmap remap is needed; in patched recompiled classes (LivingEntity, KeyboardHandler, MouseHandler, ModelBakery, Minecraft, ServerConfigurationPacketListenerImpl) they are real retargets.

## 3. Registries bridge
1. Veto: BootstrapMixin (its RETURN injector is dead because NeoForge guards wrapStreams with if(false); its @Redirect removes vanilla's freeze right before GameData.vanillaSnapshot()); MainMixin (fires before ServerModLoader.load); SimpleRegistryMixin (its addAlias override would hijack NeoForge aliases); RegistriesMixin, IdListMixin, RegistryKeysMixin; SaveLoadingMixin (replaces DataPackRegistriesHooks.getDataPackRegistries()); ExperimentalRegistriesValidatorMixin (FIELD target gone). Client: MinecraftClientMixin (early freeze; its unmap runs after revertToFrozen), ItemColorsMixin, BlockColorsMixin, ItemModelsMixin, ParticleManagerMixin. Keep RegistryMixin, RegistriesAccessor, SimpleRegistryAccessor, ChunkSerializerMixin, DebugChunkGeneratorAccessor.
2. RegistryLoaderMixin: strip only prependDirectoryWithNamespace (it produces ns/ns/path because NeoForge's elementsDirPath already prefixes the namespace). wrapIsServerCall and beforeLoad still match. If per-injector stripping is not available, veto the class and ship an Amber copy of the other two injectors.
3. Root registry: in the init window, unfreeze BuiltInRegistries.REGISTRY with the deprecated public MappedRegistry.unfreeze() and refreeze afterwards, so FabricRegistryBuilder.buildAndRegister (a direct ROOT add) works. NEVER call trackModdedRegistry (throws after NewRegistryEvent).
4. Replace impl classes: FabricRegistryInit (no payloads, no BEFORE_CONFIGURE task); RegistrySyncManager = no-op (never rely on postBootstrap, which stays false); RegistryAttributeImpl: apply SYNCED lazily as BaseMappedRegistry.setSync(true) before freezeData.
5. Events: RegistryEntryAddedCallback becomes an AddCallback adapter. RegistryIdRemapCallback pairs each onClear(full=false) with the next onBake on the same registry; BakeCallback also fires on every startup freeze; revertToVanilla shows up as clear(true) followed by AddCallback replays. IdMappingEvent is deprecated and never fired.
6. Aliases: once SimpleRegistryMixin is vetoed, FabricRegistry.addAlias resolves to BaseMappedRegistry.addAlias (identical descriptors). A Registry that is not a BaseMappedRegistry still hits Fabric's throwing default. Semantics differ: Fabric throws if the old id exists; NeoForge resolves an alias only when the name is absent.
7. One numeric-ID sync: neoforge:sync_registries. It is an early task before vanilla SynchronizeRegistriesTask and is skipped on memory connections. GAME_EVENT is SYNCED in Fabric but not NeoForge; leave it unsynced until tested against plain NeoForge clients.
8. Dynamic registries: implement DynamicRegistries.register/registerSynced via an Amber helper in package net.neoforged.neoforge.registries that calls package-private DataPackRegistriesHooks.addRegistryCodec, dedupes by key, and runs before the first world load. NETWORKABLE_REGISTRIES is live so late addition still syncs. SKIP_WHEN_EMPTY optional (unverified).
9. Tags: fire TAGS_LOADED(registryAccess, cause == CLIENT_PACKET_RECEIVED) for every TagsUpdatedEvent. Do not gate on shouldUpdateStaticData().
10. POI: redirect PointOfInterestHelper.register to a plain Registry.register. PoiTypeCallbacks already fills the blockstate map, so vanilla registerBlockStates probably throws; confirm on device.

## 4. Networking and configuration handshake
1. Veto: CustomPayloadC2SPacketMixin, CustomPayloadS2CPacketMixin, CustomPayloadPacketCodecMixin (descriptor is now codec(FallbackProvider, List, ConnectionProtocol, PacketFlow)); ServerConfigurationNetworkHandlerMixin (applies, but cancels NeoForge's query and ping(0)); all of ServerCommonNetworkHandlerMixin incl. the onPong inject (NeoForge's handlePong calls super); ClientCommonNetworkHandlerMixin, PacketByteBufMixin, PacketCodecDispatcherMixin, PlayerManagerMixin, CommandManagerMixin (dev command), and the onCustomPayload part of ServerPlayNetworkHandlerMixin.
2. Do not run CommonPacketsImpl::init or NetworkingImpl::init. NeoForge's builtin handler finishes c:version/c:register as CommonVersionTask/CommonRegisterTask, so Fabric's tasks never complete. minecraft:register/unregister are rejected (minecraft namespace) and the builtin codec always wins.
3. Payload types: buffer PayloadTypeRegistry.register calls; flush them from a RegisterPayloadHandlersEvent listener with direct NetworkRegistry.register(..., optional=true, one constant version). Skip reserved and common ids. When C2S and S2C codecs agree, register by direction with the real codec; when they differ, register bidirectional plus one Amber hook on getCodec.
4. Late registrations: insert into the per-protocol PAYLOAD_REGISTRATIONS map under a lock, or swap in concurrent maps (plain HashMaps read on netty threads). Mark optional, then send minecraft:register to live peers. FFAPI's private setup-flag flip has no late-announce.
5. Receivers: one dispatcher IPayloadHandler per id that looks up global and per-connection receivers at receive time. Configuration receivers run on the network thread as upstream; play receivers go through context.enqueueWork. Key per-connection receivers weakly or clear on disconnect. Use NetworkRegistry.register, not PayloadRegistrar (which wraps handlers for the main thread).
6. Sending: canSend = hasChannel(listener, protocol, id) (covers negotiated, c:register and ad-hoc channels); otherwise checkPacket throws. Unregistered inbound ids decode silently as DiscardedPayload.
7. Server configuration: add an Amber mixin on ServerConfigurationPacketListenerImpl implementing FabricServerConfigurationNetworkHandler (addTask -> configurationTasks.add, completeTask -> finishCurrentTask). Fire BEFORE_CONFIGURE at HEAD of runConfiguration (runs after pong(0)); CONFIGURE from RegisterConfigurationTasksEvent; DISCONNECT from handleDisconnect. Resulting order: BEFORE_CONFIGURE tasks, SyncRegistries, SynchronizeRegistriesTask, resource pack, CONFIGURE tasks, NeoForge event tasks, JoinWorld. Upstream runs CONFIGURE before registry sync; audit mods that rely on that.
8. Channel events: drive S2C/C2S*ChannelEvents REGISTER/UNREGISTER by wrapping onMinecraftRegister/onMinecraftUnregister. At JOIN synthesize play REGISTER from the negotiated NetworkPayloadSetup.
9. Play lifecycle: INIT from ServerGamePacketListenerImpl.<init>; JOIN from OnDatapackSyncEvent with player != null (two packets later than upstream).
10. Client: fire START at TAIL of BOTH initializeNeoForgeConnection and initializeOtherConnection (FFAPI misses the second); COMPLETE and READY in handleConfigurationFinished; against a real Fabric server, answer its early minecraft:register with the Fabric configuration channels before pong(0xFAB71C).
11. Keep as-is: ClientConnectionMixin (stub ChannelInfoHolder if addons removed), EntityTrackerEntryMixin, the login mixins (NeoForge has no login-class patches; confirm against coremods).

## 5. Resources, data and content
1. resource-loader: retarget ServerConfigurationNetworkHandlerMixin's @ModifyArg on new SynchronizeRegistriesTask from startConfiguration to runConfiguration. The Pack mixin probably applies unchanged (4-arg ctor delegates via this() to the 5-arg one); test before fixing.
2. Reload listeners: order is vanilla, then AddReloadListenerEvent, then Fabric's. When appending Fabric listeners, call injectContext(getConditionContext(), registryLookup) on each ContextAwareReloadListener among them and reset afterwards.
3. Known packs: Fabric's handleResponse HEAD-cancel gives the same result as NeoForge's retainAll; both on is fine.
4. Conditions: skip Fabric evaluation when neoforge:conditions is present.
5. Tags: TagFileMixin.remove() collides with the record accessor under requireAnnotations=true. Veto the module's mixins and alias fabric:remove onto the remove field codec.
6. Default item components: fire DefaultItemComponentEvents.MODIFY only from ModifyDefaultComponentsEvent. Veto item RegistriesMixin: it hooks BuiltInRegistries.freeze, which runs only at vanilla bootstrap, so the census will NOT report it.
7. Item groups: keep ItemGroupMixin (applies, runs after NeoForge's event). Veto ItemGroupsMixin (conflicts with sortTabs).
8. Loot: in modifyLootTable call setLootTableId on the new table using getLootTableId() or else the id argument; it throws on a second assignment.
9. Attachments: back each Fabric type with a NeoForge AttachmentType, queue registrations until RegisterEvent; copyOnDeath/copyHandler need a serializer, so non-persistent types get a dummy serializer plus deep-copy handler; turn auto-sync on set into syncData calls; read legacy fabric:attachments NBT once.
10. Biomes: ADDITIONS->ADD, REMOVALS->REMOVE, REPLACEMENTS->MODIFY, POST_PROCESSING->AFTER_EVERYTHING. Ship a built-in biome_modifier entry.
11. Commands: either CommandManagerMixin or RegisterCommandsEvent (fires just before setConsumer).

## 6. Client and rendering
1. FRAPI/Indigo: ship Amber's fabric-renderer-api-v1 as a binary superset of FFAPI's RenderContext; add defaults ModelData getModelData(), RenderType getRenderType(), pushModelData(ModelData), popModelData(), net.fabricmc.fabric.api.util.TriState usesAmbientOcclusion(), setUsesAmbientOcclusion(TriState). Supersede Sodium's embedded FFAPI renderer-api 3.4.1, api-base 0.4.42, rendering-data-attachment 0.3.48, block-view 1.0.10. Indigo runs only when no mod declares contains_renderer.
2. Indigo: MOVE BlockModelRendererMixin's HEAD injection to the 12-arg tesselateBlock(..., ModelData, RenderType); retarget SectionBuilderMixin to 5-arg compile and 9-arg renderBatched; emit only quads for the current pass's RenderType; FRAPI models must report every BlendMode they use through getRenderTypes.
3. VanillaModelEncoder and ForwardingBakedModel: call/forward the 5-arg getQuads, getRenderTypes, getModelData, useAmbientOcclusion (unverified).
4. rendering-v1: veto ClientWorldMixin (use ColorResolvers), BlockEntityRendererFactoriesMixin (RegisterRenderers), EntityModelsMixin (RegisterLayerDefinitions), shader.GameRendererMixin (RegisterShadersEvent). Rewrite BlockColorsMixin/ItemColorsMixin to shadow the IdentityHashMap. Move ArmorFeatureRendererMixin to 12-arg renderArmorPiece. Keep WorldRendererMixin and check its injection points on device. Pick one HUD path.
5. Key bindings: veto GameOptionsMixin (load()V runs only in the constructor). Replace registerKeyBinding's options != null throw with a processed flag; flush in RegisterKeyMappingsEvent; load(true) then restores saved keys.
6. Block render layers: veto RenderLayersMixin (its block writes miss BLOCK_RENDER_TYPES; fluid writes would work). Use BlockRenderLayerMapImpl.initialize with ItemBlockRenderTypes.setRenderLayer block and fluid setters, flush before finishModLoading. Later calls throw IllegalStateException; catch and report.
7. Screens: NeoForge's *.Post events fire only when input was not consumed. For exact Fabric semantics keep KeyboardMixin/MouseMixin and retarget into NeoForge's recompiled lambdas; otherwise adopt FFAPI's mapping. Never both.
8. Screen handlers: veto ServerPlayerEntityMixin (CAPTURE_FAILHARD cannot survive the 2-arg body). Route extended data through writeClientSideData or the consumer. Map shouldCloseCurrentScreen to shouldTriggerClientSideContainerClosingOnOpen; keep NamedScreenHandlerFactoryMixin.
9. Sound: veto SoundSystemMixin; override SoundInstance.getStream for FabricSoundInstance to call getAudioStream.
10. Model loading: the method_61072 wrap needs new lambda name lambda$bakeModels$6 and new INVOKE target ModelBakery$ModelBakerImpl.bakeUncached(UnbakedModel, ModelState). Drop the loadModelFromJson @Redirect.

## 7. Implementation order
Phase A: singleplayer world with Mod Menu, Fabric API, Lithium and NeoForge content mods. Check with javap which FAPI modules Mod Menu actually uses (screen-api and key-binding likely, unverified).
1. Shim duties (§1.7) and jar-in-jar dedupe.
2. Entrypoint window at HEAD of postRegisterEvents, plus root unfreeze.
3. Registry vetoes, no-op RegistrySyncManager, SYNCED->setSync, AddCallback adapter.
4. Networking veto set, payload forwarding, Amber configuration mixin. The integrated server still goes through configuration; only SyncRegistries is skipped on memory connections.
5. One producer each for lifecycle, tags, commands and item RegistriesMixin. Item groups.
6. Client: key bindings, colors, rendering-v1 splits, screen-api, block render layers, and either the Indigo moves or Sodium detection.
7. resource-loader retarget, conditions guard, tag alias.
Phase B: dedicated server with a remote Amber client: neoforge:sync_registries with modded ids, remap-callback pairing, dynamic-registry sync, negotiation with plain NeoForge, vanilla and real Fabric peers, configuration task-order audit, a payload over 1 MiB through GenericPacketSplitter.
Phase C: attachments, transfer, biome, content registries, loot, recipe, screen handler, sound, fluids, model loading.

## 8. Pitfalls and javap checks
Pitfalls: some mixins apply cleanly and are still wrong: BootstrapMixin, MainMixin, ServerConfigurationNetworkHandlerMixin, ServerCommonNetworkHandlerMixin.onPong, item RegistriesMixin, GameOptionsMixin, RenderLayersMixin, InGameHudMixin combined with a bridge, RegistryLoaderMixin.prependDirectoryWithNamespace. Wrapper overloads: move injectors, do not copy. Two ID syncs at once corrupt registries; keep only NeoForge's. getRegistrationOrder is captured once. The root registry stays frozen during RegisterEvent. Netty threads read plain HashMaps. FFAPI leaks per-connection receivers. Fabric CONFIGURE tasks now run after registry sync. setRenderLayer calls after loading throw.

javap on the baked 21.1.265 jar: Bootstrap (if(false) guard around wrapStreams); Main (where ServerModLoader.load is called); MappedRegistry (public unfreeze, callbacks, register(int,...)); GameData.postRegisterEvents; RegistryDataLoader.load overloads; ServerConfigurationPacketListenerImpl.runConfiguration and handlePong; whether finishCurrentTask throws on a type mismatch; CustomPacketPayload.codec 4-arg descriptor and CustomPacketPayload$1 index; NetworkRegistry.setup and PAYLOAD_REGISTRATIONS; Pack constructors; TagFile.remove(); PoiTypes.registerBlockStates (throw); ModelBlockRenderer, SectionCompiler, HumanoidArmorLayer, BlockRenderDispatcher overloads; ServerPlayer.openMenu; SoundInstance.getStream; BlockColors/ItemColors field types; Options.load(Z)V; ItemBlockRenderTypes.BLOCK_RENDER_TYPES; lambda names in KeyboardHandler, MouseHandler, ModelBakery, EntityRenderers, ReloadableServerRegistries (lambda$scheduleElementParse$3/$4); BuiltInRegistries.freeze call sites; whether LevelRenderer still has the WorldRendererMixin targets.

javap on the FAPI jars: FabricRegistry.addAlias (should be a throwing default); KeyBindingRegistryImpl; the RenderContext method sets in the official jar and in Sodium's embedded jar.
